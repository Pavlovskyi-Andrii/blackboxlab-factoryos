# Telegram, Relay и команда /proof

Как задача из Telegram становится тикетом Relay, как владелец отвечает и принимает результат, и как `/proof` проверяет всю цепочку по фактам сервера.

## Что это

- **Relay** — журнал задач FactoryOS. Каждая задача — тикет с номером вида `R-0001` и неизменяемой историей событий.
- **Telegram-бот** — пульт владельца. Он работает только в одном привязанном личном чате; сообщения из других чатов игнорируются.
- Привязка делается один раз командой `/pair КОД` (код показывает FactoryOS, он действует 10 минут).

## Как задача попадает в Relay и обратно в Telegram

1. Обычный текст, ссылка, голосовое, видео, документ или фото в привязанном чате создают тикет. Исполнитель по умолчанию — Claude.
2. `/new текст` создаёт тикет без исполнителя, бот предлагает кнопки «🟠 Claude» и «🔵 Gemini (через GitHub)».
3. Повтор одного и того же сообщения от Telegram не создаёт второй тикет (проверка по `update_id`).
4. Когда воркер отмечает этапы (взял задачу, работает, commit, push, готово, нужна помощь, ошибка), сервер присылает в чат карточку этапа.
5. Если Telegram принял это сообщение, сервер записывает в тикет событие `owner_notified`. Это квитанция доставки, её потом читает `/proof`.

## Как владелец отвечает и принимает

- Кнопки тикета: «▶️ В работу», «🙋 Нужно от меня», «✅ Готово», «↩️ Inbox», «↻ Retry», «✖ Cancel queued», «🔄 Обновить».
- Если воркер написал «нужна помощь» — ответьте, что нужно, или нажмите «↻ Retry».
- Пока задача в работе, «✅ Готово» не сработает: сначала дождитесь результата.
- Если у результата есть PR, после CI и мержа задача закроется сама и придут кнопки «✅ Принял» / «👎 Не то». «👎 Не то» возвращает тикет в «Нужно от меня».
- Если PR нет, закрыть можно вручную с причиной: `/done R-0001 причина`.

## Что делает /proof

Отправьте `/proof R-0001`. Бот ответит отчётом приёмки по одному тикету. Отчёт собирается только из истории тикета на сервере; бот ничего не спрашивает у модели и не вызывает Telegram, GitHub или Render.

| Этап | Откуда факт |
|---|---|
| сообщение из привязанного чата | источник тикета: канал, chat id, update id |
| ровно один тикет | нет других тикетов с тем же сообщением |
| claim воркера (run_id) | событие `claimed` с id воркера и `run_id` |
| running | событие `running` того же `run_id` |
| done | финальное событие того же `run_id`, в правильном порядке по времени |
| итог воркера | текстовый итог в событии `done` |
| уведомление доставлено в Telegram | квитанция `owner_notified`, не позже часа после финала |

- Итог: «✅ ПОДТВЕРЖДЕНО сервером», только если все 7 этапов есть и проблем нет. Иначе «❔ НЕ подтверждено» и список проблем.
- Блок «Код» показывает commit и ветку (со слов воркера) и ссылку на PR. PR, CI, merge и deploy остаются «не проверено», пока их не записал сервер.
- Время в UTC, секреты вырезаются. Тот же отчёт владелец получает через `GET /api/relay/{id}/acceptance`.

## Почему «назначено» — это ещё не «выполняется»

- Назначение только ставит тикет в очередь: в карточке пишется «Назначено (запуск не подтверждён)».
- «Выполняется» начинается, только когда воркер сам забрал задачу и сервер записал `claimed` с `run_id`, а затем `running`.
- Если воркер долго не присылает heartbeat, задача показывается как «⚠️ Worker без связи» (stale), а не как работающая.
- У Gemini нет Relay-runner: тикет, назначенный Gemini, сам не запустится. Gemini работает через GitHub-задачи с меткой `gemini`.

## Где смотреть

- В Telegram: `/tasks`, `/task R-0001`, `/history`, `/proof R-0001`.
- На сайте: доска `/relay` (Inbox, In progress, Need you, Done) после входа владельца.

## Ограничения

- Живая приёмка владельцем ещё не пройдена: это задача T-591-H, её статус виден в «Ваши задачи».
- `/proof` не проверяет PR, CI, merge и deploy сам: он только показывает, записаны ли эти факты.
