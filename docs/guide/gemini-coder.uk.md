# Як працює Gemini-кодер

Цей документ описує процес автоматичної обробки задач за допомогою Gemini-кодера у FactoryOS.

## Схема роботи

### 1. Мітка `gemini` на Issue
- Задачу позначають міткою `gemini` у GitHub Issue.
- Перший рядок опису задачі має бути `Owner: Gemini`; без нього цикл задачу не бере.

### 2. Цикл на EC2 (кожні 5 хвилин)
- Воркер на EC2 регулярно (раз на 5 хвилин) перевіряє задачі з міткою `gemini`.
- Береться відкрита задача з найменшим номером, для якої ще немає гілки `gemini/issue-N`. Якщо гілка вже є, задача пропускається — повторно її не виконують.
- За один запуск — до 15 спроб звернення до моделі з паузою між ними.

### 3. Проксі FactoryOS
- Воркер звертається до проксі FactoryOS (`/api/factory/gemini/worker/...`), не маючи прямого доступу до API-ключа Gemini.
- Дозволено використовувати лише стабільні Flash-моделі Gemini.

### 4. Створення гілки `gemini/issue-N` і PR
- Згенерований код оформлюється в гілку `gemini/issue-N`.
- Створюється Pull Request (PR) із внесеними змінами.

### 5. Перевірка Claude
- Модель Claude перевіряє підготовлений PR, проводить рев'ю і ухвалює рішення про злиття.

## Що робити, якщо Google перевантажений

- У разі помилок або тайм-аутів Google Gemini (коди 502/504 upstream): не хвилюйтеся, воркер автоматично повторить спробу в наступному циклі (через 5 хвилин).
- Безкоштовна денна квота Gemini скидається опівночі за тихоокеанським часом (08:00 UTC). Якщо квота закінчилася ввечері, Gemini простоює до ранку — це не поломка.
- Якщо API і далі недоступний, можна зняти мітку `gemini` із задачі або передати її на виконання іншому агенту (наприклад, Claude).

## Безпека

- API-ключ Gemini зберігається лише в конфігурації Render / FactoryOS і ніколи не передається воркеру на EC2 чи в публічний репозиторій.
