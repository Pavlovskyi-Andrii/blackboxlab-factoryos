# Як влаштований FactoryOS: гайд по проєкту

Ця сторінка пояснює всю систему з одного погляду:
- хто що робить;
- де це дивитися;
- які правила не можна обійти.

Подробиці про кожну частину є в інших гайдах розділу «Як це працює».

> Звірено з кодом 2026-11-14. Якщо щось тут розходиться з тим, що видно на панелі, правильна панель: отже, гайд застарів.

## 1. З чого складається система

| Частина | Що це | Де живе |
|---|---|---|
| **Панель FactoryOS** | Сайт, де ви все бачите й погоджуєте | Render, `blackboxlab-factoryos.onrender.com` |
| **Сервер** | FastAPI-застосунок (`app.py` і модулі поруч) | Render. Деплой відбувається лише після зеленого CI на `main` |
| **EC2-воркер** | Окрема машина, де агенти реально працюють: Claude, браузер, MyCast | AWS EC2, цикл `autopilot/` |
| **GitHub** | Код, задачі (issues), PR, перевірки CI | `blackboxlab-factoryos` |
| **Telegram-бот** | Ставить задачі агентам і надсилає результати та MyCast | Relay-бот |
| **Notion** | Концепції, рішення, дослідження, пам'ять проєкту | Notion workspace |

## 2. Хто що робить

- **Ви (власник).** Ставите цілі й пріоритети. Погоджуєте публікації, витрати, великі релізи та все, що виходить назовні. Без вашого «так» нічого не публікується.
- **Claude.** Пише код в окремій гілці, відкриває PR, запускає тести, робить рев'ю архітектури й виконує задачі з Telegram через Relay.
- **ChatGPT / Codex.** Пишуть специфікації та прототипи й роблять автоматичне рев'ю PR. Блокувальні зауваження Codex виправляються до злиття.
- **Gemini.** Безкоштовний помічник: робить дослідження, чернетки й документацію, озвучує MyCast.
- **Браузерний агент.** Читає сторінки в браузері на EC2, зокрема під збереженою сесією. Він лише читає й нічого не публікує.

## 3. Який шлях проходить задача

1. **Задача.** Ви пишете її в Telegram або створюєте issue на GitHub.
2. **Relay.** Задача стає тикетом `R-xxxx` зі статусом `queued`. Це означає «призначено», але ще не «виконується».
3. **Claim.** Воркер на EC2 забирає тикет, і статус стає `claimed`, потім `running`. Лише з цього моменту робота реально йде.
4. **Гілка і PR.** Агент вносить зміни в окремій гілці й відкриває PR.
5. **CI.** GitHub Actions проганяє перевірки. Червоний CI означає, що зливати не можна.
6. **Рев'ю.** Codex та/або людина перевіряють PR. Блокувальні зауваження виправляються.
7. **Злиття → деплой.** Після злиття в `main` Render сам деплоїть нову версію, але лише після зеленого CI.
8. **Відповідь у Telegram.** Ви отримуєте підсумок: PR, посилання або зрозумілу причину помилки.

**Якщо задача впала через ліміт.** Claude отримує до 60 ходів і 30 хвилин на один прогін. Якщо цього не вистачило, бот так і пише. Розбийте задачу на кроки або натисніть Retry.

## 4. Розділи панелі

| Група | Що там |
|---|---|
| **Огляд** | Control Room, конвеєр, Supervisor, центр помилок |
| **Створення контенту** | Задачі (jobs), Discovery, Revideo, Content Brain, Media Finisher, варіанти, пакет, файли |
| **Перевірка й публікація** | Review: погодити або переробити. Publish: розклад і квитанції публікацій |
| **Зростання й навчання** | Performance з реальними метриками, Analytics, Experiments |
| **Автоматизація й команда** | Autopilot (завжди зупиняється на перевірці), агенти, воркери, браузерний агент |
| **MVP Builder** | Проєкти MVP зі стадіями й доказами, MyCast |
| **Система** | Build Progress, Release QA, консоль власника (Telegram-задачі, Claude ↔ Codex, слухачі MyCast), бренд-стратегія, налаштування |
| **Навчання** | Ця сторінка: ваше навчання, навчальні матеріали по системі, гайди |

## 5. Контент-фабрика

1. **Бренд-стратегія.** 7 кроків: мета → розпакування → аудиторія → тон → стовпи → воронка → CTA. Погоджені кроки збираються в **Master Brief**. Кожен агент контенту отримує свою частину брифу.
2. **План на 30 днів.** Із плану створюються задачі. Задача, створена з рядка плану, пам'ятає, до якого бренду вона належить.
3. **Виробництво.** Сценарій → голос → відео → фініш (субтитри, звук, безпечні зони).
4. **Review.** Ви погоджуєте або відправляєте на переробку.
5. **Publish.** Окрема явна дія після погодження. Автопублікації немає.
6. **Performance.** Лише реальні метрики з платформ. Немає метрик — немає «навчання».

## 6. MVP Builder

- Кожен проєкт має стадію: ідея → дослідження → специфікація → збірка → прев'ю → перевірка власником → validated/rejected.
- Стадію рухає лише подія з доказом: посиланням на PR, коміт, CI або артефакт.
- Фінальні стадії (`validated` / `rejected`) ставите лише ви.
- **A/B Tester** поки що лише специфікація (PR #347, розбір у #348). Порівняння двох аудиторій — це «порівняння сегментів», а не рандомізований A/B-тест.

## 7. MyCast

- Ваш особистий випуск приходить у Telegram до 06:00 за Києвом. Докладніше в гайді «MyCast для власника».
- Сайт для слухачів: `mycast.pro`. Вхід через Telegram, Google потрібен лише для календаря.
- Реферальна програма: друг одразу отримує +7 днів. Той, хто запросив, отримує +7 лише після першого реального випуску друга.

## 8. Правила, які не можна обійти

- Публікація, витрати й будь-які повідомлення третім особам потребують вашого явного погодження.
- Платні виклики моделей не вмикаються автоматично. Content Brain має бюджетний ліміт.
- Секрети не пишуться в чат, не потрапляють у репозиторій і не показуються на екрані. Вони зберігаються в Render або в зашифрованому сховищі (vault).
- У `main` не пушать напряму: лише через PR із зеленим CI.
- Тести не можна вимикати чи послаблювати заради зеленого CI.
- Метрики, квитанції публікацій та успіх деплою не можна вигадувати. Де даних немає, пишеться «немає даних».

## 9. Де дивитися, якщо щось не так

| Питання | Де відповідь |
|---|---|
| Що зараз роблять агенти? | Консоль власника → Telegram-задачі. Ще є Агенти й Воркери |
| Чому задача впала? | Повідомлення в Telegram (там пряма причина), центр помилок |
| Що змінилося в коді? | GitHub → PR і `DECISIONS.md` |
| Що в плані? | Build Progress (`ROADMAP.md`) |
| Скільки витрачено на Actions? | GitHub → Billing. CI запускається лише на PR і `main`, скриншоти лише на `main` |
