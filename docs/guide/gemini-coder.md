# Как работает Gemini-кодер

Данный документ описывает процесс автоматической обработки задач с помощью Gemini-кодера в FactoryOS.

## Схема работы

1. **Метка `gemini` на Issue**
   - Задача помечается меткой `gemini` в GitHub Issue.
   - Первая строка описания задачи должна быть `Owner: Gemini`; без неё цикл задачу не берёт.

2. **Цикл на EC2 (каждые 5 минут)**
   - Воркер на EC2 регулярно (раз в 5 минут) проверяет задачи с меткой `gemini`.
   - Берётся открытая задача с наименьшим номером, для которой ещё нет ветки `gemini/issue-N`. Если ветка уже есть, задача пропускается — повторно её не делают.
   - За один запуск — до 15 попыток обращения к модели с паузой между ними.

3. **Прокси FactoryOS**
   - Воркер обращается к прокси FactoryOS (`/api/factory/gemini/worker/...`), не имея прямого доступа к API-ключу Gemini.
   - Разрешено использование только стабильных Flash-моделей Gemini.

4. **Создание ветки `gemini/issue-N` и PR**
   - Сгенерированный код оформляется в ветку `gemini/issue-N`.
   - Создается Pull Request (PR) с внесенными изменениями.

5. **Проверка Claude**
   - Модель Claude проверяет подготовленный PR, проводит ревью и принимает решение о слиянии.

## Что делать, если Google перегружен

- При возникновении ошибок или таймаутов Google Gemini (коды 502/504 upstream): не волнуйтесь, воркер автоматически повторит попытку в следующем цикле (через 5 минут).
- Бесплатная дневная квота Gemini сбрасывается в полночь по тихоокеанскому времени (08:00 UTC). Если квота кончилась вечером, Gemini простаивает до утра — это не поломка.
- Если недоступность API продолжается, можно снять метку `gemini` с задачи или передать её на исполнение другому агенту (например, Claude).

## Безопасность

- API-ключ Gemini хранится только в конфигурации Render / FactoryOS и никогда не передается воркеру на EC2 или в публичный репозиторий.
