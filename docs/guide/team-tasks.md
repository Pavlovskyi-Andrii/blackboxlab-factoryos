# Документация: страница «Задачи команды» (`Team Tasks`)

Данное руководство предназначено для Владельца и описывает устройство страницы «Задачи команды», значение отображаемых элементов, статусы задач и источники данных.

---

## 1. Откуда берутся данные

Модель данных собирает информацию исключительно из чтений следующих источников:

* **GitHub API**:
  * **Issues**: Задачи репозитория. Исполнитель (agent) определяется по первой строке описания (`Owner: Claude`, `Owner: ChatGPT`, `Owner: Gemini`).
  * **Pull Requests**: Запросы на слияние. Исполнитель определяется по префиксу ветки (`claude/`, `chatgpt/`, `gemini/`).
  * **Check Runs (CI)**: Статусы автотестов и проверок CI на головных коммитах открытых PR.
* **EC2-снимок / Полосы агентов (Lanes / Heartbeat)**:
  * Статус активности агентов (онлайн/офлайн) и время последнего «пульса» (`heartbeat_age_seconds`).
* **ROADMAP.md**:
  * Задачи с пометкой `[HUMAN]`, ожидающие действий Владельца.
* **Owner Desk (Карточки решений Владельца)**:
  * Карточки решений, разъясняющие шаги разблокировки или утверждения задач.

---

## 2. Что значат плитки агентов

На странице расположены плитки для каждого агента (**Claude**, **ChatGPT**, **Gemini**) и для **Владельца (Owner)**.

Каждая плитка содержит:
* **Индикатор онлайн-статуса**: Показывает, активен ли агент в данный момент на основе heartbeat с EC2.
* **Текущая задача (Current)**: Активная задача в работе (`in_progress`, `review`, `ci_failed`).
* **Следующая задача (Next)**: Первая в очереди задача (`queued`).
* **Последняя выполненная (Last Done)**: Недавно завершённая задача (`done`).
* **Счётчики по статусам**: Количество задач в разных состояниях и суммарное количество выполненных задач за последние 7 дней (`done_7d`).

---

## 3. Статусы задач и прогресс

Шкала прогресса отображает этап выполнения задачи:

| Статус | Прогресс | Значение |
| :--- | :--- | :--- |
| `queued` | 0% | Задача в очереди, ещё не взята в работу. |
| `blocked` | 0% | Задача заблокирована меткой `blocked`, зависимостями или условием Владельца. |
| `waiting_owner` | 0% | Задача ждёт действия Владельца (`ROADMAP [HUMAN]` или карточки решений). |
| `in_progress` | 40% | Агент выполняет задачу (создан Draft PR). |
| `ci_failed` | 60% | PR готов или в черновике, но проверки CI упали. |
| `review` | 85% | PR готов и ждёт проверки (ревью). |
| `done` | 100% | Задача завершена (PR смерджен или Issue закрыта). |

---

## 4. Причины и уточнения статусов (`reason`)

Для точной диагностики рядом со статусом выводится текстовая причина:

* **«CI упал» (`ci_failed`)** — Упали проверки CI в GitHub Actions.
* **«CI выполняется» (`ci_running`)** — Проверки CI ещё идут на коммите PR.
* **«Ждёт проверки Claude» / «Awaiting review» (`awaiting_review`)** — PR готов к проверке ревьюером или владельцем.
* **«Черновик PR» (`draft_pr`)** — Открыт Draft PR, работа в процессе.
* **«Цикл Gemini» (`gemini_loop`)** — Задача во внутреннем цикле обработчика Gemini.
* **«Не началась» (`not_started`)** — Задача в очереди, работа ещё не начата.
* **«Действие Владельца» (`owner_action` / `owner_decision`)** — Требуется решение или действие Владельца.
* **«Заблокирована меткой» (`blocked_label`)** — На Issue стоит метка `blocked`.
* **«Ожидает зависимостей» (`depends`)** — Задача ждёт закрытия связанных issues/tasks (`Depends: #...`).
* **«Условие Владельца» (`owner_gate`)** — В заголовке есть ограничение на старт (например, `CONDITIONAL` или `только после`).

---

## 5. Вкладки и Queue Keeper (Хранитель очереди)

* **Вкладки агентов**: Переключают отображение между всеми задачами команды и детальными списками отдельных участников (Claude, ChatGPT, Gemini, Owner).
* **Queue Keeper (Хранитель очереди #231)**: Определяет, какие открытые задачи готовы к взятию в работу прямо сейчас (цель по умолчанию — 10 готовых задач). Автоматически разделяет задачи на:
  * `ready` — полностью готовы к старту;
  * `blocked` — заблокированы (метки, незакрытые `Depends:`, условия владельца);
  * `in_review` — уже имеют открытый или смердженный PR.

---

## 6. Кнопка «Обновить сейчас»

* Данные о задачах кэшируются для снижения нагрузки на GitHub API с периодом обновления **180 секунд (TTL)**.
* Нажатие кнопки **«Обновить сейчас»** принудительно запрашивает свежие данные с GitHub и снимка EC2.
* Чтобы избежать превышения лимитов API, установлен минимальный интервал повторного обновления — **20 секунд** (`min_refresh`).
