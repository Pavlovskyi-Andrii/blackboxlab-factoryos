## Місце у FactoryOS
Показувати окремий розділ **MVP Factory** під Agent Office, візуально відмінний від **Content Factory**. Не створювати другий автономний планувальник. Повторно використовувати наявні події Relay, ідентичності воркерів, схвалення, посилання на GitHub Issue/PR і журнал аудиту.

## Ролі та передавання роботи
1. **MVP Manager** (оркестратор, а не нова підписка на LLM): відповідає за чергу і статус, вибирає наступне придатне завдання, фіксує докази.
2. **Product Analyst / Spec Writer**: перетворює ідею на проблему, покупця, пропозицію, обсяг робіт, метрику успіху, залежності та експеримент з перевірки на 24–72 години.
3. **Claude Builder**: призначається лише після схвалення специфікації, пише веб-прев'ю в ізольованій гілці й відкриває чорновий PR. Жодного подвійного володіння завданням воркерами.
4. **QA / Security**: незалежно перевіряє тести, секрети, права доступу до маршрутів і готовність. Відсутність CI — це BLOCKED, а не зелений статус.
5. **Deploy Agent**: пропонує прев'ю на наявній безкоштовній інфраструктурі; жодних нових хмарних ресурсів і публічного деплою без схвалення власника.
6. **Content Factory**: отримує маркетинговий бриф лише після перевірки прев'ю і схвалення власника; ніколи не публікує автоматично.

## Машина станів
`idea -> researching -> spec_draft -> spec_review -> build_queued -> building -> qa_review -> preview_ready -> owner_review -> validated | rejected`.
У стан `blocked` можна перейти з будь-якого незавершального стану, вказавши причину, час і джерело.
Не переводити стан далі на підставі самого лише твердження LLM; потрібне конкретне посилання-доказ або схвалена дія. «Невідомо» не означає «виконано».

## Приймання та перевірки
- Панель інтерфейсу показує три пілоти й чітко позначає статус seed/demo.
- Окремо від Content Factory та Agent Office; локалізація EN/UK/RU під час інтеграції.
- Перехід за кліком до канонічних GitHub Issues; жодних фальшивих таймерів, витрат токенів чи сигналів життя воркерів.
- Один реальний пілот демонструє шлях: специфікація -> PR з кодом -> CI -> перевірене прев'ю -> рішення власника.
- Безпека та CI залишаються обов'язковими. Жодних витрат, повідомлень, публікацій чи змін інфраструктури без схвалення.
