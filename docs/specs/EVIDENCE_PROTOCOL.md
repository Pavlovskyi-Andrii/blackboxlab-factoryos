# FactoryOS Evidence Protocol — ТЗ по тирам

**Статус:** проект ТЗ, не реализовано. Нужно решение владельца по Тиру 1.
**Источник:** предложение ChatGPT (2026-11-09), критика и дополнения Claude.
**Принцип:** No Evidence — No Done. Задача не завершена, пока результат не подтверждён в источнике, а не со слов агента.

---

## Что изменено относительно исходного предложения

| Было в предложении | Стало | Почему |
|---|---|---|
| Новая система: Evidence Collector, 7 статусов | Блок проверки внутри существующего тикета Relay | Relay уже имеет `run_id`, `event_id`, `pr_url`, проверку CI/merge; две машины состояний разойдутся |
| Один статус `VERIFIED` | Уровни доказательства: `claimed` → `linked` → `checked` → `accepted` | Не всё проверяется машиной; честнее сказать, какой уровень достигнут |
| «Проверка воспроизведения» MyCast | Существующий QC (#233) + оценка владельца | Качество звука машина не измерит |
| «Фактическое получение» в Telegram | `message_id` = отправлено; получение = кнопка владельца | Bot API не подтверждает прочтение |
| Проверяющий читает GitHub | Только собственное чтение Render | Снимок EC2 делает сам воркер — это не независимая проверка |
| Продавать как продукт | Только после месяца своих данных | Нужна цифра «заявлено, но не подтверждено» |

---

## Уровни доказательства

| Уровень | Кто ставит | Что значит |
|---|---|---|
| `claimed` | агент | «Я сделал» — без ссылок |
| `linked` | агент | Есть ссылки: PR, SHA, файл, id доставки |
| `checked` | только сервер FactoryOS | Сервер сам прочитал источник и правило выполнено |
| `accepted` | только владелец | Владелец подтвердил (кнопка или команда) |

Агент **не может** выставить `checked` или `accepted` — ни через событие воркера, ни через API.

## Тир 1 — Фундамент (делаем первым)

**Объём:** 1–2 PR. **Расходы:** ноль, новых сервисов нет. **Опирается на:** Relay, журнал доставок MyCast, проверку PR на сервере.

### T1.1 Блок `verification` в тикете Relay
```json
"verification": {
  "type": "code",
  "required_level": "checked",
  "level": "linked",
  "checks": [
    {"name": "pr_merged", "source": "github:render", "sha": "…", "observed_at": "…", "result": "pass", "detail": ""}
  ],
  "override": null
}
```
**Готово, когда:** тест — событие воркера с `level: checked` отклоняется; уровень `checked` появляется только после серверной проверки.

### T1.2 Правила по типам задач — в коде (`evidence_rules.py`)
| Тип | Обязательный уровень | Обязательные проверки |
|---|---|---|
| `code` | `checked` | PR смержен; CI зелёный на этом SHA |
| `mycast` | `checked` | доставка `sent:true`; QC пройден для этого выпуска |
| `telegram` | `checked` | есть `message_id` от Bot API |
| `publish` | `accepted` | одобрение владельца (существующий гейт) |
| прочее | `linked` | хотя бы одна ссылка-доказательство |

**Готово, когда:** таблица правил покрыта тестами; неизвестный тип → `linked`, не `checked`.

### T1.3 Проверки только читают готовые результаты
- `code`: данные PR/CI, которые уже читает сервер (Relay round trip).
- `mycast`: журнал доставок + результат QC.
- `telegram`: ответ Bot API.

Ничего не перезапускается: ни CI, ни генерация аудио, ни платные вызовы.
**Готово, когда:** тест с «шпионом» — проверки не делают ни одного запуска, только чтение.

### T1.4 Гейт на `done`
- Перевод в `done` при уровне ниже обязательного → отказ с причиной.
- Владелец может закрыть вручную **с обязательной причиной**; пишется в `override` и в историю.

**Готово, когда:** тест — `done` без доказательств отклонён; закрытие владельцем без причины отклонено, с причиной — проходит и видно в истории.

### T1.5 Доказательства привязаны к SHA
Новый push в PR → проверки типа `code` помечаются `stale`, уровень падает до `linked`.
**Готово, когда:** тест — смена head SHA сбрасывает `checked`.

### T1.6 Критерии готовности задаются до работы
- В шаблоне задачи «Готово, когда» — список пунктов из T1.2 (не проза).
- Обязательные проверки сохраняются в тикете при создании; менять их может только владелец.

**Готово, когда:** тест — агент не может убрать обязательную проверку.

## Тир 2 — Независимость и видимость

**Объём:** 2–3 PR. **Расходы:** ноль. **Может понадобиться от владельца:** read-only токен GitHub на Render.

### T2.1 Независимый источник для `checked`
- `checked` — только по данным, которые Render прочитал **сам** (`FACTORY_GITHUB_TOKEN`).
- Данные из снимка EC2 → максимум `linked` с пометкой «по данным воркера».
- **Владельцу:** проверить, что на Render есть рабочий read-only токен GitHub (сейчас при ошибке чтения сервер переходит на снимок EC2).

### T2.2 Проверка деплоя
Сейчас никто не сравнивает SHA на Render с main (найдено в #242). Добавить проверку «Render работает на коммите X» (SHA только для владельца, не в публичном `/health`).

### T2.3 Кнопка владельца «✅ получил / 👎 не то»
Для брифинга, MyCast и задач типа `publish`. Даёт уровень `accepted`; «не то» возвращает задачу с причиной.

### T2.4 Отображение
- Карточка тикета в Telegram и в Agent Office: уровень + список проверок (источник, время).
- В макетах — только явно фиктивные данные, никаких реальных номеров PR рядом с выдуманными статусами.

### T2.5 Метрики
- **Ложное «готово»:** агент сообщил `done`, проверка не подтвердила.
- Число ручных закрытий владельцем.
- Время от «сделал» до `checked`.

Показывать в утреннем брифинге (#106).

### T2.6 Перекрёстное ревью для важных задач
Правило может требовать проверку `peer_review`: ревью PR другим агентом (например, Gemini для PR от Claude) через обычный GitHub review. Включается по типу задачи, не для всех.

## Правила безопасности (для всех тиров)

- Агент не пишет `checked`/`accepted` и не меняет результаты проверяющего.
- Проверки только читают; никаких перезапусков, платных вызовов и публикаций.
- Гейты одобрения владельца (публикация, оплата, инфраструктура) не ослабляются и не подменяются уровнем `checked`.
- Секреты и сырые chat id не попадают в доказательства и логи.
