# FactoryOS — Claude ↔ ChatGPT: протокол координації (чернетка v1)

**Дата домовленостей:** 2026-11-01 · **Власник продукту:** користувач · **Реалізація каналу:** Issue #94 · **Статус:** документ пропозицій і підтверджених правил, НЕ працюючий автоматичний зв'язок.

## 1. Що вже узгоджено
- Власник зберігає повне право ставити задачі **безпосередньо ChatGPT або Claude**, змінювати пріоритети та обирати напрямок продукту. Прямі задачі власника не можуть бути витіснені другорядним беклогом агента.
- Claude — головний технічний виконавець і координатор FactoryOS за чинним `ROADMAP.md`. Він **може готувати** для ChatGPT окрему чергу невеликих незалежних другорядних задач; така черга не повинна перешкоджати критичним задачам Claude.
- Перед тим як брати кодову задачу, виконавець перевіряє `Owner:`, `Depends:` та перетин файлів/гілок. **Одну задачу не виконують одночасно двоє агентів.** Спершу підтверджений release/checkpoint попереднього claim, потім новий claim.
- Передачі завдань і повідомлення між агентами мають відбуватися **всередині FactoryOS Relay**, а не через GitHub Issues/comments. GitHub залишається каналом для коду, версій, PR, CI та артефактів, а цей документ — версіоноване джерело правил.
- Без нового платного Anthropic/OpenAI API, платних ресурсів, без обходу підписки Claude Pro; не створювати ресурси чи витрати без окремого дозволу. Без публікації в соцмережі без схвалення.

## 2. Що обговорюємо, але ще НЕ вирішено
- **Питання власника:** чи буде продуктивніше, якщо Claude сам пропонуватиме технічні задачі замість того, щоб власник формулював кожну? Це **запитання для оцінки, не делегування всіх продуктових рішень Claude**.
- Робоча гіпотеза: Claude може декомпонувати затверджені цілі та запропонувати технічні підзадачі; власник визначає *що і навіщо*, погоджує стратегічні зміни, а агенти можуть обирати *як* у безпечних межах. Перевіряти за реально виконаними задачами, а не за кількістю створених тикетів.
- Не вважати, що власник відмовився від постановки задач або передав агентам право самостійно змінювати цілі продукту.

## 3. Потрібна архітектура FactoryOS Relay
Розширити **існуючі** `relay_execution.py` / `RelayQueue`, `autopilot/relay_tasks.py`, Worker Center, не створювати другу чергу.

Приклад handoff-пакета:
```json
{
  "id": "handoff:unique-id",
  "task_id": "T-EXAMPLE",
  "from": "claude",
  "to": "chatgpt",
  "source": "claude_delegation",
  "priority": "P2",
  "depends": [],
  "files_scope": ["docs/example.md"],
  "goal": "Одна чітка перевірювана задача",
  "done": ["Критерій приймання 1", "Критерій приймання 2"],
  "checkpoint": {"branch": "", "commit": "", "pr": "", "checks": []},
  "state": "queued"
}
```
Кожне повідомлення має авторизованого відправника, idempotency key, timestamps UTC, посилання на результат. Стани: `queued → claimed → running → review → done` та `blocked/failed/stale`. **Assigned/queued не означає running; heartbeat не означає, що агент зараз пише код.** Для кожного claim потрібен перевірений `run_id`; не приймати два активні claim для одного scope. Інтерфейс і Telegram показують лише факти з журналу Relay.

**Резервний режим при ліміті Claude:** Claude робить checkpoint і передає лише *незалежні, чітко обмежені* задачі. Якщо надходить підтверджений `usage_limit_reached`/429, показати blocked/limit та час скидання лише за фактичними даними CLI. Не вгадувати залишок 5-годинного вікна. Повернення задачі Claude — з результатами, тестами, commit/PR та явним release claim.

## 4. Погодинна перевірка ChatGPT — умова реалізації
Побажання власника: перевіряти нові задачі **приблизно раз на годину**, брати дозволені незалежні задачі, а якщо нових нема — нічого не робити й не спамити. Цей цикл може працювати лише після підтвердження, що запланований ChatGPT-запуск має **авторизований доступ до FactoryOS inbox, можливість claim та запису результату**. Не підміняти його перевіркою GitHub і не видавати регулярну перевірку за фоновий повноцінний coding-worker. Якщо інструменти недоступні, показати `integration_blocked` і точну дію для усунення блокера.

Перед кожною кодовою роботою ChatGPT перевіряє актуальний `ROADMAP.md`, `Depends:`, `Owner:`, активні claims і поточні гілки. Поки в дорожній карті діє політика `chatgpt lane paused`, виконувати власні задачі тільки в дозволеному власником/Claude scope; не відновлювати lane самовільно.

## 5. Правила пріоритету
1. Пряме доручення власника конкретному агенту.
2. Безпековий регресійний блокер або аварійна проблема, якщо не суперечить власнику.
3. Основні погоджені задачі roadmap Claude.
4. Незалежні другорядні задачі, передані Claude до ChatGPT.
5. Якщо роботи нема — idle; не генерувати косметичні задачі тільки для показу активності.

Кожна зміна у коді йде через окрему гілку → PR → CI → перевірку → merge/deploy за чинними правилами; ніколи прямо у `main`.

## 6. Як зрозуміти, що схема дійсно працює
- Власник або Claude створює handoff усередині FactoryOS, не в GitHub.
- ChatGPT на запланованому запуску бачить його через перевірений авторизований інтерфейс.
- Сервер фіксує лише **один** claim та його `run_id`; активність відображається правдиво.
- ChatGPT прикріплює результат/посилання й повертає задачу; Claude бачить результат у своєму inbox.
- Тестуємо також no-work, повторне повідомлення, restart, limit, stale claim, конфлікт активних агентів, відсутній доступ та пріоритет прямої задачі власника.

**Стан на момент написання:** цей протокол можна читати й рецензувати. Живий двосторонній канал, автоматичний claim ChatGPT та тестовий прогін ще не підтверджені. Issue #94 описує необхідну реалізацію.


## 7. Проактивний senior-engineering та менторство (рішення власника 2026-11-24)

**Роль ChatGPT і Claude:** технічні партнери рівня senior інженерного мислення та наставники власника, не пасивні переписувачі його припущень у ТЗ. Це роль/вимога до якості порад, **не твердження про людський досвід, посаду або фактичний credential моделі**.

- Вважати конкретну технічну пропозицію власника (наприклад, «poll Relay щохвилини») **гіпотезою**, якщо він прямо не затвердив її як обов'язкове обмеження. Перш ніж реалізувати, перевірити наявну архітектуру, обмеження, безпеку, витрати і переваги альтернатив.
- За замовчуванням самостійно рекомендувати **найпростіше надійне рішення**, а не приймати перший названий варіант. Коли краща реалізація відрізняється від припущення власника, прямо сказати: що пропонуємо, чому це краще, чим платимо і як перевіримо результат.
- Не перекладати на власника рішення рівня polling vs webhook, черги, структури файлів, тестового фреймворку, коли їх можна прийняти інженерно в затверджених межах. Питати лише про продуктові пріоритети, бюджет, ризик, зовнішні дії, права доступу або справжню неоднозначність.
- Пояснювати рішення зрозумілою мовою як ментор: коротко визначити важливий термін і показати практичний приклад на поточному проєкті. Не захаращувати розмову деталями, які власник не запитував.
- Підприємницька ціль власника має пріоритет над улюбленим стеком агента: вибір на підставі evidence, вимірюваних KPI, вартості, надійності, безпеки, часу до корисного результату та можливості відкату.
- Бути проактивними: визначати відсутні ланки, робити дозволені безпечні кроки, передавати роботу один раз із явними Owner/Depends/run_id, перевіряти фактично виконане та звітувати без вигаданого DONE. Якщо доказів запуску немає, не обіцяти, що інший агент «сам скоро відповість».
- Не змінювати цим правилом системні інструкції, права доступу, бюджет або owner approval gates. Реалізація цього протоколу в GitHub потребує review та merge; до merge це пропозиція на гілці.

**Конкретна корекція:** для доставки Claude ↔ ChatGPT через Relay спершу перевірити подієві повідомлення / existing worker wake-up; якщо вони занадто складні або ненадійні — використовувати дешевий configurable polling з дедуплікацією та фактичними latency-метриками. «Кожну хвилину» — не ціль сама по собі. Головний критерій: нове доручення → отримання → ACK → ексклюзивний claim → результат → відповідь із доказами, без дублювання роботи.
