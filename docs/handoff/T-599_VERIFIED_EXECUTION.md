Главное правило: **не строить вторую очередь.** Очередь с атомарным захватом, `run_id`, обнаружением зависших задач и журналом событий уже есть — это `RelayQueue` в `relay_execution.py`. Задача — провести через неё задачи из ROADMAP и GitHub Issues и показывать только её события.

## 0. Диагноз (проверено по коду `main` на 2026-10-30)

1. **Воркер не читает GitHub Issues.** Цикл в `autopilot/autopilot.py` берёт работу из двух источников: тикеты Relay (`relay_tasks.run_one`), затем `ROADMAP.md` (`next_safe_task`). Issue #67 не попадает ни туда, ни туда. Импорт есть (`POST /api/relay/intake/github-issue`, Telegram `/issue N`), но запускает его только владелец вручную. Поэтому у #67 и нет события `claimed`: его никто не ставил в очередь.
2. **У задач из ROADMAP нет захвата на сервере.** У тикета Relay есть `claim` с `run_id`, событиями и статусом `stale`. Задача из ROADMAP выполняется локально: на сервер уходят только heartbeat и `.autopilot/status.json`. Поэтому FactoryOS не может доказать, что Claude взял, например, T-594.
3. **Одна заблокированная задача останавливает всю очередь.** Если первая подходящая задача вернула `blocked`, воркер запоминает `blocked_task` и бесконечно спит на ней: `next_safe_task()` каждый раз снова возвращает её же. Остальные задачи не выполняются.
4. **T-590 без `Owner:`.** Её выбирают обе линии (`claude` и `chatgpt`). Оставшиеся пункты T-590 требуют действий владельца (PR в `main`, привязка Telegram T-506, живая проверка). Значит, вероятнее всего, воркер сейчас стоит в состоянии blocked на T-590 (см. п. 3) и до T-594…T-598 и #67 не доходит. **Это нужно подтвердить по журналу EC2, а не принимать на веру.**
5. **T-564 зависит от несуществующей T-563,** поэтому её никогда не выберут, хотя коммит `fc43f1f` по ней уже есть. Это вопрос к линии ChatGPT; Claude эту задачу не трогает.
6. Ошибку разбора `Depends:`/`Owner:` в середине строки (T-591…T-593 могли запуститься раньше T-590; у T-591-A владелец читался как `chatgpt.`) исправляет PR #68. Его нужно влить первым.

## 1. Решения, которые устраняют противоречия в ТЗ

| Вопрос | Решение |
|---|---|
| Единый источник состояния выполнения | `RelayQueue` (`DATA_DIR/relay.json`, переживает перезапуск). ROADMAP и GitHub хранят *что* делать, `RelayQueue` хранит *кто и когда взял и что сделал*. Интерфейс и Telegram читают только её |
| Задачи без исполнителя | Каждая открытая задача получает `Owner: claude \| chatgpt \| gemini \| any`. Метку `Unassigned` не вводим. После PR с разметкой задача без `Owner:` **не выбирается никем**, а в Build Progress показывается как «Исполнитель не назначен». `any` значит «кто первым захватит на сервере» |
| `Executor:` / `Planner:` | Исполнителем не считаются. Исполнителя задаёт только `Owner:` |
| Чужие задачи | Claude не меняет `Owner:` и не ставит галочку у задач с `Owner: chatgpt`/`gemini`. T-560-*, T-562, T-564 остаются за ChatGPT |
| Названия событий | Используем уже существующие стадии `RelayQueue`, названия из ТЗ — это подписи в интерфейсе (таблица в §3) |
| Кто подтверждает PR/CI/merge/deploy | Сервер, по GitHub API и данным Render, а не по словам агента. Без подтверждения стадия показывается «не проверено» (так уже сделано в `lifecycle`) |
| Автоматический merge | **Не входит в эту задачу.** Решает владелец. До его явного решения Claude создаёт PR и ждёт merge от владельца |

## 2. Порядок работ (каждый пункт — отдельный PR, ветка `claude/T-599-<x>-...`)

### T-599-A — Убрать остановку очереди на одной задаче *(самое маленькое, разблокирует работу сразу)*
- Добавить в `next_safe_task()` параметр `skip: set[str]`. Заблокированная задача, у которой не изменились `runtime_marker()` и `answers.md`, пропускается, и воркер берёт следующую подходящую.
- `failed_hold` работает так же: задача после 3 неудач ждёт команду Retry от владельца, но не мешает остальным.
- Тест в `autopilot/test_autopilot.py`: T-1 blocked → выбирается T-2; изменение в `answers.md` снова открывает T-1; задача `[HUMAN]` никогда не выбирается.

### T-599-B — Разметка исполнителей в ROADMAP *(только `ROADMAP.md` и тест; таблицу утверждает владелец)*
- Проставить `Owner:` всем открытым задачам по направлениям, которые утвердил владелец:
  - `claude`: T-590, T-591, T-592, T-593, T-594…T-599, T-536-B, T-535
  - `chatgpt`: T-560-D, T-560-E, T-562, T-564, T-591-A, T-540, T-541, T-542, T-551-A, T-552, T-553, T-554, T-581…T-589
- Существующие `Owner:` не менять.
- Изменить `owned_by_operator`: пустой `Owner` больше не означает «общая задача». Общая задача — только явный `any`/`auto`.
- Тест: в реальном `ROADMAP.md` нет открытой задачи без `Owner:`; для `claude` и `chatgpt` выбираются разные первые задачи.

### T-599-C — Задачи ROADMAP проходят через серверный захват
- Добавить в `RelayQueue` метод `intake_roadmap_task(task_id, title, owner, depends)` по образцу `intake_github_issue`: `source_key = "roadmap:T-xxx"`, идемпотентный — повторный вызов возвращает уже существующий тикет.
- Добавить в `RelayQueue.claim()` параметр `operator`: тикет можно захватить, только если `owner` совпадает с линией воркера или равен `any`. Захват атомарный (под тем же lock), не больше одного активного запуска на `source_key`. Второй захват получает отказ, а в журнал пишется событие `claim_rejected`.
- Воркер (`autopilot.py`) перед `run_agent(target)`:
  1. регистрирует задачу через `POST /api/relay/intake/roadmap` (с токеном воркера);
  2. захватывает её через `POST /api/relay/worker/claim` и получает `run_id`;
  3. **без `run_id` код не трогает**: пишет `status=idle`, причину «claim rejected/unavailable» и ждёт.
- Если сервер недоступен, ROADMAP-задачи **не выполняются** (fail-closed) и в статус пишется понятная причина. Иначе снова появится работа без доказательств.
- Heartbeat продлевает аренду задачи. Задача без heartbeat дольше `stale_seconds` получает статус `stale`. Повторно её **не запускают автоматически**: только по Retry от владельца (так уже работает `enqueue`).

### T-599-D — События из родительского процесса, а не со слов агента
События отправляет `autopilot.py` (родительский процесс, который видит git и exit code), а не текст ответа Claude. Пишутся с `run_id` и `event_id` через существующий `RelayQueue.event`:

| Стадия `RelayQueue` | Подпись в интерфейсе (ТЗ) | Когда пишется |
|---|---|---|
| `claimed` | TASK_CLAIMED | сервер выдал `run_id` |
| `running` | CODING_STARTED | запущен `claude` CLI |
| `checkpoint` + `{"checks":"started"}` | TESTS_STARTED | старт DONE-команды/проверок |
| `checkpoint` + `{"checks":"passed\|failed"}` | TESTS_PASSED / TESTS_FAILED | код возврата проверок |
| `committed` | — | новый SHA в ветке |
| `pushed` | — | push удался |
| `pr` | PR_CREATED | номер и URL PR (сервер сверяет с GitHub) |
| `ci` / `merged` / `deployed` | — / PR_MERGED / DEPLOY_VERIFIED | только по данным GitHub/Render, которые проверил сервер |
| `blocked` | TASK_BLOCKED | `status=blocked` или нужна помощь человека; причина в `note` |
| `failed` | — | неудача; счётчик попыток виден |
| `done` | TASK_COMPLETED | только когда галочка в ROADMAP действительно закрыта (`done_status_is_consistent`) **и** выполнен DONE-критерий задачи |

Поля каждого события: `ticket_id`, `source_key` (T-ID или Issue), `worker_id`/линия, `run_id`, `event_id`, `at` (UTC), `commit`/`pr_url`, если есть, и короткий `note` после `redact`. Секретов, токенов и содержимого `.env` в событиях быть не должно.

### T-599-E — Автоматический приём GitHub Issues *(замена ручному `/issue N`)*
- Сервер периодически (не чаще 1 раза в 5 минут, бесплатный GitHub API) берёт открытые Issues **только от автора-владельца репозитория** со строкой `Owner: Claude|ChatGPT|Gemini` в первой строке текста и вызывает `intake_github_issue` (повторный вызов ничего не дублирует).
- Если Issue ссылается на T-ID, у которого уже есть тикет `roadmap:T-xxx`, новый тикет не создаётся: Issue привязывается ссылкой (например, #67 → T-594/T-595/T-596).
- Issues от других авторов не берутся (защита от внедрения чужих задач).

### T-599-F — Интерфейс и Telegram показывают только события *(пересекается с T-596 и третьей частью #67; делать в их рамках, не отдельно)*
- Workers / Build Progress: состояние исполнителя вычисляется из последних событий и heartbeat:
  - **Working** — есть активный `run_id` и свежий heartbeat;
  - **Blocked** — последнее событие `blocked`/`failed`;
  - **Stale/Unknown** — heartbeat старше порога;
  - **Idle** — online и нет активного запуска;
  - **Offline**.
- Задача с `Owner:`, но без `claimed` показывается как **«Назначено, не взято»** и никогда как «В работе».
- ChatGPT показывается «в работе» только при его собственном подтверждённом событии (PR/commit в ветке `chatgpt/...`). Активность не выдумывать.
- Telegram: отдельное сообщение на `claimed`, `blocked`, `failed`, `pr`, `done`. Повторные события не дублируются (по `event_id`). `/status` показывает каждую линию: текущую задачу, стадию, время старта, последнее подтверждённое действие и PR. Если heartbeat устарел — Stale. Работает только после привязки Telegram (T-506 [HUMAN]); без неё уведомления пишутся в журнал, и в интерфейсе видно, что Telegram не привязан.

## 3. Приёмочные тесты (детерминированные, без сети и платных вызовов)

- **А. Обычная задача:** открытая `Owner: claude` → intake → claim (`run_id`) → `running` → проверки → `committed` → `pushed` → `pr`. Build Progress и `/status` показывают ту же задачу и стадию.
- **Б. Конфликт:** два воркера (`claude`, `chatgpt`) одновременно захватывают одну задачу `any` — успешен ровно один, второй получает отказ и `claim_rejected`. Задачу `Owner: chatgpt` воркер `claude` не захватывает никогда.
- **В. Перезапуск:** пересоздать `RelayQueue` на том же `DATA_DIR` посреди `running` → состояние и журнал на месте. Повторного запуска нет; без heartbeat задача становится `stale`, и её не перезапускают без Retry.
- **Г. Блокировка:** ошибка GitHub/push → `blocked` с причиной, видимой в API и тексте Telegram. Воркер берёт следующую задачу (проверка T-599-A).
- **Д. Актуальность:** новая задача в ROADMAP или Issue владельца со строкой `Owner:` появляется в Build Progress с правильным исполнителем и статусом «Назначено, не взято» без ручной правки карточек.
- **Е. Нет выдуманной активности:** задача с `Owner:`, но без событий нигде не отображается как running; события без верного `run_id` отклоняются.

Плюс стандартный набор из `CLAUDE.md` (`py_compile`, `test_planner`, `smoke_tests`, проверка встроенного JS в дашборде) и существующие наборы тестов Relay.

## 4. Ограничения

- Не создавать платные ресурсы и не включать платные API. Использовать существующий EC2-воркер.
- Не трогать код T-560-*, T-562, T-564 (`Owner: chatgpt`). Можно только *показывать* их состояние.

- Не удалять историю тикетов, не создавать дублирующие PR, не ставить `done` без выполненного DONE-критерия.
- После каждого PR — короткий отчёт в Issue #67: номер PR, SHA, какие проверки запускались, CI, что подтверждено вживую, а что нет.
